=====================================================================
 A. WHAT THE SANITY CHECK COVERS  (npm run sanity, about 7 min, up to ~14 when a carrier search times out)
=====================================================================
 It replaces the ~40 min manual walkthrough. It NEVER pays: it stops at Traveler Details (status Created)
 and captures booking refs (K + 9 digits; the China ref starts with Z).

  Browser, B2B account (customer care ROW):
   - 19 point-to-point carrier sectors + 3 rail passes, built into batched carts -> booking refs
     (a sector is only DROPPED after the primary route AND all backup routes failed)
   - SNCF Connect POS check
   - read-only production API searchability (LocoHub; needs the VPN / corporate network)
  In parallel (read-only, do not touch the B2B cart):
   - Key account ROW, Agents portal ROW, Key account China, Customer care China: logged in with a saved
     session, a real search must return trains (Customer care China also books 1 train, never pays)
   - Group Bookings-Salesforce Sync (AWS AppFlow), Dropfile sanity check (Ariane Glue job), Primer status
  Last step: opens the Outlook draft and DMs you the result ("Sanity OK/KO HH:MM IST").

 THE MAIL HAS 9 POINTS, each OK, KO or [check manually]:
    1 B2C & B2B check (customer care ROW booking refs)   2 Group Bookings-Salesforce Sync
    3 Key account ROW     4 Agents portal ROW     5 Key account China
    6 Customer care China (China ref, Z...)       7 SNCF       8 Primer       9 Dropfile sanity check
 NOT in the sanity any more: the connectivity page and LocoHub staging (removed 2026-10-28), the "SF cases
 not linked with an SR" line (removed from the mail 2026-10-29; extra-checks still records it in
 report\msc-extras.json, it is just not mailed).
 Needs AWS login for points 2 and 9, and the portal logins for points 3-6, else they read [check manually].

 6. IF THE RUN IS STUCK (seen 4 Oct)
=====================================================================
 - Symptom: sits at "2/5 API searchability" for many minutes.
 - Cause: laptop cannot reach LocoHub (internal 10.x addresses) = VPN / network dropped.
 - Check (prints True when OK):
      powershell -Command "(Test-NetConnection production.locohub-prod.aws.raileurope.com -Port 443).TcpTestSucceeded"
 - Fix: reconnect VPN, press Ctrl+C in the run window (answer Y), then rerun npm run sanity.
 - Check nothing is left running:
      tasklist /FI "IMAGENAME eq node.exe"
 - Kill a leftover run completely (/T = whole process tree):
      taskkill /F /T /PID <number>
 - A killed or Ctrl+C run does not send the DM/mail. Booking refs it created stay valid,
   but a rerun creates new ones - use the NEW refs.

 8. WHAT THE RESULTS MEAN
=====================================================================
 - Mail subject: OK / KO. KO = an automated item failed OR the booking suite did not
   capture a booking ref.
 - "[check manually]" = the run could not verify it (login expired, tool not set up).
 - A sector is only DROPPED/ERROR after the primary route AND all backup routes failed.
   A dropped carrier is written on mail point 1 as "KO carrier - RENFE via Renfe VaV: <reason>" and in the DM
   under "check yourself" (since 2026-11-08). The mail subject and the line's own OK/KO are NOT flipped by it:
   the subject is yours to edit in the Outlook draft, so judge it yourself.
 - Any issue or KO (a carrier that could not be booked, with its reason; a KO point; a check that could not be made;
   a retry that was needed) is also listed under "Notes (issues / KO)" at the END of the mail and in the DM (since 2026-11-08).
   The subject OK/KO is only a suggestion: edit it in the Outlook draft.
   Customer care China tries its booking twice; a failure says which page it was stuck on and saves
   reportchina-booking-fail-<attempt>.png.
 - Each carrier is searched on its OWN test date, because carriers sell different distances ahead (measured 2026-11-08):
   RegioJet Wien-Gyor 14 d (sells ~23), RegioJet Prague-Brno 30 d (~53), SNCF 30 d (~53), Renfe 40 d (~70), all others 45 d
   (Leo Express ~83, TER ~105, ... DB/SNCB/Iryo/Trenitalia 330+). A sector dropped with "no <carrier> trains" usually means the
   carrier window moved: re-measure and edit daysAhead in datajourneys.js (see the table in its header comment).
 - "Traveler Details did not open ... retrying once" in the run = the portal showed "Sorry,
   something unexpected happened"; the run retried. Only a second failure counts.
 - B2C is NOT really tested: the API check uses LocoHub (the B2B route); the B2C website
   calls the carriers itself.
 - The cart order is simply the list order (the run no longer reads the connectivity page).
 - Primer: a status-page notice with impact "none" (e.g. a planned maintenance notice) does not make
   the line KO.
 - China KO with title "Loading | Rail Europe": portal slow to boot. Wait is now 120s.
   If you see it again, check the portal by hand and tell Claude.
 - Point 1 reads OK when B2B was proven by the booking run, even if the B2C API half could
   not run (then it is listed under "still to check" in the console).
 - Point 1 showing [check manually] / API not run: look at report\api-searchability.json. If it
   says "envs": [] the Postman folder was not found. Expected folder:
   %USERPROFILE%\OneDrive - RAILEUROPE\Desktop\Training Material\Postman Collections\LH
   (your own user folder; or point POSTMAN_DIR at wherever your exports are).
